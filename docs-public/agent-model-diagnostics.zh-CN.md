## 结论与证据

这次不是简单的“模型选错了”。旧代码把较长的规划输出放在 10 秒调用预算内，而且证据裁剪可能只保留元数据、丢掉实际摘要；解读入口又允许模型未经校验地编写和推送诊断正文。GLM 本身的延迟波动和自由文本越界是真实限制，需要由调用契约和报告校验共同处理。

没有发现常规 10 秒规划请求丢失 `thinking.type=disabled` 的 SDK 问题。新增 HTTP 线级测试使用实际 DeepSeek 客户端和预算 Advisor 检查请求体。另发现并修复了客户端边界错误：请求超时为 0、等于或超过配置值时，原来会复用允许思考的主客户端。不过旧回放的配置为 60 秒、规划为 10 秒，不经过这个分支，不能把八次超时归因于它。

对照使用现有 GLM-4.6、关闭思考、同一份隔离测试证据，未更换模型，也未一律放宽规划超时：

| 调用 | 实际观测 | 可以说明什么 |
| --- | --- | --- |
| 原首次规划提示词，4096 输出上限 | 一次 45 秒超时，一次 11.824 秒 | 原任务在这些样本中超过 10 秒预算 |
| 原后续规划提示词，4096 输出上限 | 13.745 秒 | 返回可由 Agent 提取的 JSON，但已超时 |
| 原首次提示词，仅改上限为 768 | 10.177 秒 | 单改输出上限不能保证解决问题 |
| 精简后的对象步骤格式，768 上限 | 首次 7.432/8.644 秒，后续 9.210 秒 | 输入和输出契约调整后出现预算内成功样本 |
| 同一精简提示词，4096 上限 | 9.041 秒 | 不能将全部收益归因于 token 上限 |
| 事实编号选择，512 上限 | 4.206 秒，24 个输出 token | 短结构化输出可替代自由编写诊断事实 |

这些是小规模顺序对照，有供应商排队、网络和缓存差异，不能据此声称达到延迟 SLO。最终实现进一步使用能力名数组、最多一个新候选、512 输出上限，须以最终 JAR 的完整链路结果为准。

原始请求/响应和计时保留在 `artifacts/model-diagnostics/20261020-baseline/`、`20261020-fixed/`。复核见 [测量汇总](../artifacts/model-diagnostics/20261020-reviewed-measurements.json)。原计时文件不重写；首次探针曾把新版系统提示词长度算入旧提示词的长度，汇总从保存的请求重新计算，耗时不受影响。严格 JSON 解析失败和 Agent 支持的代码围栏 JSON 也分开记录，不把可提取的 JSON 误记为无效响应。

## 实际改动

1. **规划只请求必要内容。** 能力目录保留名称与短说明，证据 ID、质量和样本量与事实摘要分别输出，避免头部占满截断额度。请求模型以能力名返回步骤，最多提出一个已有假设之外的新候选。程序补齐通用理由和必查项，继续校验能力白名单、目标、只读性和总预算，兼容旧对象步骤格式；总候选数仍受既有六项上限约束。
2. **按调用场景控制输出。** `SpringAiJsonCompletion` 支持独立输出上限，规划设为 512；所有场景客户端始终关闭思考，超时不超过宿主配置。普通主对话客户端仍保留原能力。
3. **诊断事实不能由模型重写。** `DiagnosticReport` 从冻结证据生成事实目录。模型只选事实编号；编号有效、无重复、JSON 完整且未被截断时，程序生成正文。逐版本样本分母、5xx、样本率、响应来源、故障阶段、证据引用和假设状态均来自程序。所有已保留的版本观测组一并展示，避免只挑故障组、隐去对照组。
4. **明确观测和根因的区别。** 当前状态不能证明历史正常；BASELINE 或未观察到变更不能证明没有变更；制品名和发布时间不能证明因果。业务根因未获直接证明时保持未知，不承诺缩流就能恢复，也不把提案当执行回执。
5. **先验证，再发布。** 解读 JSON 和模型思考不再直接进入 SSE。校验通过后一次发布与落库相同的正文；错误、伪造引用或供应商失败保持规则调查结果并标明模型失败。已经取证的工具对话同样使用确定性报告；调权提案状态使用工具真实结果。

模型仍负责选择调查能力、提出新候选和挑选相关事实。自由编写的业务根因论证暂不作为权威诊断展示。这是收紧结论权限，不代表模型自由推理质量已经被修好；也不能据此宣称自动修复已经完成。没有产生诊断取证的普通对话仍使用模型回答，不在本轮受约束诊断保证内。

事实目录上限为 24 项，时间线最多列四项非基线变更，长来源文本截断并标明。原始证据继续保留；超大调查的分层摘要、完整引用覆盖及更丰富的业务根因验证仍需后续评测。
