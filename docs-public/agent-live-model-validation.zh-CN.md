# 真实模型故障调查验收

测试开始日期：2026-10-18。环境为单 Admin JVM + H2，模型沿用本机已保存的 GLM-4.6 配置，未配置快速模型。所有业务请求、路由、账号和故障均来自独立测试环境。

## 验证范围

- 实际访问模型服务商，先验证连接，再通过 HTTP 告警入口执行调查规划和流式解读。
- v2 返回 503、v2 响应超过 Gateway 超时两个场景各重复两次，每阶段 120 次真实业务请求。
- 一次交互式调查，要求模型实际使用只读工具、取回证据、给出回答，且路由版本不变。
- 最后通过本机模拟服务商返回 503，检查证据保留、AI 失败标记和规则回退；该探针使用假密钥。
- 实际 Gateway 重启、操作回执与参数一致性仍沿用原有严格检查。

模型参与调查和解读。停止坏版本流量及恢复权重由测试脚本执行，不能计为 Agent 自主修复。

## 真实接入发现并修复的问题

第一轮联网测试虽然成功调用模型，却出现错误诊断：模型看到“没有实例”，将上游业务返回的 503 解释为无可用实例。这轮结果不能作为诊断质量通过的证据。

根因在取证逻辑：Admin 路由快照把多版本分组表示为 `v1,v2`，实例叙述和规则判断却将其与单个实例的 group 做整体相等比较，导致两台健康实例都被过滤掉。

本次修复：

1. 实例叙述、健康计数、规则判断共用多分组匹配逻辑，保留单分组和空分组语义。
2. 追踪证据新增窗口内保留记录的完整状态码分布，避免将最近五条示例误当整体比例。
3. 模型提示明确区分上游返回 503 与 Gateway 拒绝，禁止将告警名称作为已确认根因。
4. 真实模型告警使用中性描述，不把故障名称或注入答案交给模型。
5. 回放要求实例证据识别出两个健康版本；模型解读失败或退回规则不能冒充真实模型通过。
6. 真实调用发现 JDK `HttpTimeoutException` 被计为普通错误、未走一次超时重试；补齐异常识别，并验证连续超时计为 `timeout`。
7. 默认对话模型原来使用空指标实现，实际对话完成后没有调用统计；组合根现在给默认模型传入宿主指标，新增装配回归覆盖。
8. 对话当前时间未包含时区，模型把几分钟前的 UTC 告警误算成八小时前；现改为 ISO offset 时间，并明确 Z 的含义。
9. 回归触发同步阻塞等待与任务截止定时器的竞态；模型等待异常后先检查并结算预算，避免已到期任务尚未标记停止。

中间轮还出现从“半数请求返回 504”推断“延迟剧烈抖动”的过度归因。本次进一步明确症状与根因的区别，要求缺少同窗口实例或逐跳证据时保留根因不确定性。

## 证据对照与剩余模型质量问题

本轮由 Codex 对照客户端请求、任务证据和模型文本复核，并非人工签署的生产准入。四份故障解读的 120 条样本、58 次错误、两个当前健康实例与记录一致，均明确保留根因不确定性。对照记录在完整回放目录的 `validation-review.json`。由于当前历史追踪摘要未暴露逐跳和按实例的完整窗口证据，模型不能据此确认具体是 v2 或其业务代码为何失败。

模型接入门禁通过不等于诊断文本全部正确，仍存在可复核的问题：

- 一份 504 解读把“路由不存在”也描述为应返回 503，而 Rover 的未匹配路由实际返回 404（`RouteAndProxyFilter`）。
- 一份 503 解读建议查看 `upstream_status`，当前 Rover 接口与访问日志契约并未提供这一字段保证，建议混入了其他网关的通用经验。
- 部分推断仍将比例相近与实例异常模式关联，必须按候选假设理解，不能替代同窗口的直接证据。

因此本轮确认的是接入、取证、预算/失败收尾和可观测链路可用，**不把模型诊断质量标为生产自动处置准入通过**。S2 应继续补齐按实例/逐跳窗口证据、结论引用验证、项目能力约束和真实模型回归样本集；同时针对 GLM-4.6 的规划短超时评估快速模型与场景超时配置。

## 边界

这次仅检验两个固定故障场景和一次对话，不能替代更大规模的模型评测、长期稳定性和生产容量验证。确认出现 503/504 与确认业务根因是不同结论；证据不足时必须保留不确定性。供应商故障探针模拟的是 HTTP 503，不代表已覆盖所有网络和供应商故障。

模型凭据仅用于本机测试进程，原始配置保持不变；隔离副本在结束时删除。原始产物包含 H2 和测试运行配置，默认被 Git 忽略，分享前应只选取脱敏证据。
