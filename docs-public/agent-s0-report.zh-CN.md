## 1. 基线与部署边界（S0-01）

本批仍以单个 Admin 进程承载 Agent API、调查线程池与确定性动作执行器，H2 保存运行记录。没有引入共享 PostgreSQL、持久 Job、租约、跨节点 SSE 或团队权限。当前升级后 Agent schema 为 v6，升级前源码实际为 v5。

默认调查线程数为 2，排队容量 16，任务登记容量 200；每个任务默认 180 秒、最多 20 次模型调用、100000 总 token，规划最多 3 轮、10 次能力调用、6 步计划。这些是配置上限，尚未进行容量认证，不能表述为已测吞吐。生产方案提出的 5 个并行调查、100 条告警/秒仍是待验证目标。

| 能力 | 本批后的真实状态 | 尚缺的生产能力 |
| --- | --- | --- |
| 告警调查 | 登录调用者可触发；来源与单一处理账号分开；处理账号可查看并追问 | 独立机器认证、团队队列、RBAC、认领和交接 |
| 时间窗口 | 指定范围进入规划、取证、规则、解读与对话工具 | 历史指标适配、完整覆盖与证据质量契约 |
| 历史数据 | 日志按目标/范围查询；内存追踪与注册事件按范围筛选 | 不保证缓冲和采样完整；无法仅凭无样本排除故障 |
| 自动提案 | 仍需用户提出调权意图；只登记待批准动作 | 调查结束自主生成证据充分的处置计划 |
| 执行保护 | 审批状态 CAS + 全程行版本条件写回 + Gateway revision | 计划 hash、策略授权、持久 Worker、资源范围与租约 |
| 异常对账 | 原执行/补偿 operationId 保留，可人工回查 | Gateway 长期持久回执、后台定时对账与超时升级 |
| 验证 | 回读目标权重一致才算动作成功 | 错误率、延迟、样本量等业务效果验证 |
| 记忆与审计 | 现有资源笔记、会话和动作记录 | 经过效果验证的案例、Runbook 版本、不可变独立审计 |

固定故障集按以下类别继续建设：未命中路由、无实例、坏实例、坏版本、超时、容量不足、发布相关、多故障、数据源缺失、过去故障但当前健康。新增测试覆盖最后两类中的时间边界，以及告警越权、交错回查/回滚、提交后落库失败；不将模拟端口测试计作真实故障演练。

## 2. 告警归属与人工继续调查（S0-02）

- `POST /api/agent/events/ingest` 从认证上下文获取来源主体，不接受载荷指定的 `userId`、`triggeredBy` 或处理账号。匿名调用不受理。
- 每条告警仍创建独立 Session/Incident。默认处理账号为认证来源；配置 `rover.agent.alerts.owner-user-id` 或环境变量 `ROVER_AGENT_ALERT_OWNER` 可将新告警统一归属一个现有值班账号。
- `Incident.triggeredBy` 单独保存认证来源；更新范围、挂任务、汇总结论和重启都不能丢失该字段。处理账号保存在 Session.userId，二者含义不同。
- 处理账号可以读取任务、订阅 SSE、打开工作台、继续提问；其他账号按不存在处理。工作台事件面板展示来源账号和处理账号。
- v6 只增加可空 `triggered_by` 列。历史事件保持来源未知；不会从原处理账号伪造来源，也不自动迁移旧的无归属会话。

配置应填系统中已存在的账号；本批没有账号创建、团队映射或多处理人授权。配置只影响之后受理的告警，不重新分配已有会话。保留内部无认证 Java 重载用于兼容，HTTP 不使用它。

## 3. 时间一致的调查（S0-03）

`TimeRange` 校验非负起止与顺序，HTTP 起止字段必须成对提供；`0/0` 保留原有“未指定”哨兵语义。未指定时使用各数据源默认口径，指定时贯穿：

```text
告警/高级上下文 → Incident/InvestigationTask → PlanningRequest
  → 规则或模型规划 → CapabilityExecutor / OpsTools
  → 范围内证据 + 当前上下文标记 → FindingsInput → 规则与模型解读
```

日志使用绝对时间窗口，模型传入的“最近几小时”不能替换任务显式窗口。追踪和注册事件过滤窗口外记录，叙述与规则采用同一窗口。目标解析不出时也保留显式范围；追问继承已有事件范围。已采集日志和知识进入解读上下文。

路由、实例、配置只有当前快照，证据标注 `CURRENT_CONTEXT` 并明确不能验证历史。窗口日志/追踪/事件标注 `REQUESTED_WINDOW`，知识标注 `REFERENCE`，同时保存请求起止值。该标注只表示适用范围，不保证采样覆盖完整。

当前 MetricReadPort 仅有实时滚动窗口，指定绝对范围时不调用它，返回“不能回溯”的限制。历史规则不使用当前健康排除故障；时段内采到 503 只确认观察事实，其他无法验证的假设保持 UNKNOWN，不能把 503 直接升级为根因。

## 4. 交错写回与操作号（S0-04、S0-05）

`AgentAction.version` 暴露已有数据库行版本。新对象 version=0 只能插入，返回 version=1；更新必须匹配读到的版本，每次成功写入递增。删除或版本冲突时拒绝写入，不能退化成插入，避免旧对象复活。内存与 JDBC 实现遵循相同契约。

批准和回滚入口继续原子检查状态，并增加版本条件；执行器保存提交号、进入验证、写入结果等每一步都使用仓储返回的新版本。迟到 resolve 的写回冲突后读取最新状态，不能盖掉已开始或完成的补偿。

异常兜底使用最新持久化记录，保留执行号与补偿号；旧回查异常不得降级已经开始的补偿阶段。后续只按原号查询并回读，不重发副作用。数据库完全不可用时仍可能无法保存 UNCERTAIN；这时保留之前写下的操作号，由已有启动恢复分类，持久后台对账需在 S1 完成。
