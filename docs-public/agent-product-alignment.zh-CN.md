# 对照成熟 SRE Agent：差距、调整与验收

日期：2026-10-20。源码基线 `131d6db`。部署继续采用单 Admin + H2；不引入 PG、多个 Agent 进程或新框架。本轮是 S2 调查能力的补强，主线完成数仍为 17/42，S2 仍为 4/6，不能把对标报告或参数调整算成新阶段交付。

## 官方产品怎样设计

本次查阅官方产品文档、工程文章和服务卡。它们说明了对外能力或设计方向，不代表已取得厂商内部实现；宣传案例的效果也不能直接移植为 Rover 的指标。

| 产品与官方依据 | 可以借鉴的设计 | 对 Rover 的启示 |
| --- | --- | --- |
| [Azure 深度调查教程](https://learn.microsoft.com/en-us/azure/sre-agent/tutorial-deep-investigation) | 多源取证、多个假设、分层验证、可取消并保留部分结果；明确说明深度调查需要数分钟 | 将深度调查与轻量请求分开，不用交互等待时间强行压缩调查；长任务应持续显示进展 |
| [Datadog 调查架构](https://www.datadoghq.com/blog/building-bits-ai-sre/) | 按假设定向查询并深入子假设，避免将所有遥测一次塞给摘要模型 | 保留调查所需的统计、时间范围和引用，按证据缺口选择下一步；多调工具本身不代表查得更好 |
| [Datadog 评测平台](https://www.datadoghq.com/blog/engineering/bits-ai-eval-platform/) | 冻结故障时的可见信号，保留人审根因标签、噪声和调查轨迹，观察改动是否让其他场景退化 | 评测应比较关键证据是否被查到、是否停在表面症状、是否误归因，而不止检查 JSON 合法或调用成功 |
| [AWS DevOps Agent 服务卡](https://docs.aws.amazon.com/ai/responsible-ai/aws-aidevops-agent/overview.html) | 资源范围和工具权限约束，引用证据、说明局限，写入经人工审批；以已知故障和专家标签评测 | 保留现有授权与确定性执行，继续补充业务可观测数据和多场景评测，不能用模型自信代替证据 |
| [PagerDuty SRE Agent](https://www.pagerduty.com/platform/ai-agents/sre/) | 结合历史事故和 Runbook，运行已批准自动化，再确认服务恢复 | 历史案例应有来源、有效期和验证结果；执行回读之后还要观察业务恢复 |

本次资料没有给出可直接照抄的统一模型请求超时、输出 token 或思考开关。以下 60 秒、2048 token、300 秒等都是 Rover 的可调起点，依据自身调用链设置，不能称为厂商标准。

也需纠正原先材料中的绝对说法：[Azure 的 Review 模式](https://learn.microsoft.com/en-us/azure/sre-agent/run-modes)明确包括 Azure CLI 等基础设施操作。受控执行的关键在于身份、范围、工具策略、批准和审计，不是所有产品都禁止任何命令。Rover 继续采用类型化 API 与执行器，现阶段不需要引入通用 Shell。

## 当前真实差距与优先级

| 优先级 | Rover 目前的不足 | 应补能力与现有阶段 |
| --- | --- | --- |
| P0，本轮处理 | 目标识别和规划共用 10 秒；规划可自动路由到快速模型，且仅有 512 输出 token | 分开调用预算、模型角色和思考开关；较长规划不因一次超时重复从头推理 |
| P0，本轮处理 | 仅取前八项证据、每条摘要 160 字，关键线索和版本分母可能在后面 | 保留有界结构化统计、较完整摘要、时间范围与假设引用；优先相关证据并明示省略 |
| P0，S2-05 | 外部应用日志、Prometheus、链路和服务拓扑尚未形成完整受控读取 | 同环境、同资源、同时间窗的只读连接器与查询模板，分页、预算、脱敏和 SSRF 检查；无数据不能当健康 |
| P0，S2-06 | 两类故障重复回放不能代表复杂调查质量；单测通过无法证明模型理解了因果 | 冻结场景与可见信号，加入本地拒绝、依赖故障、容量不足、无关变更、证据冲突及不足；绑定模型、提示词、查询模板与调用策略版本，同时评调查轨迹、质量、耗时和费用 |
| P1，S2-06/S3 | 新 M 候选始终 UNKNOWN，最终报告固定保守表达；仍不能自动验证复杂业务病因 | 建立带引用、反证、缺口的业务解释契约，补直接证据和验证规则后再允许升级结论。事实目录是当前表达约束，不是诊断能力的最终形态 |
| P1，S3 | 正常调查尚不能自动生成完整待审批处置方案，动作类型单一 | 证据准入、计划版本、策略和多动作契约；模型提案与执行权限分开 |
| P1，S4 | 调权回读只证明控制面生效，尚不能证明业务恢复 | 执行前基线、执行后观察窗、样本量、错误率/延迟及干扰检查；无效时补偿或升级人工 |
| P1，S5 | 资源笔记尚不是可靠的历史案例与版本化 Runbook | 记录适用条件、来源权限、过期、修复效果和人审反馈；相似历史只能提供线索 |
| P1，S6 | 大规模告警风暴、长期运行、成本和供应商故障的生产门禁未完成 | 代表性数据上的质量回归、容量、排队时延、预算、失败隔离、审计及备份演练 |

本轮没有实现 Azure 式的完整深度调查模式、并行假设树或运行中人工转向；现有图仍有三轮、十次能力调用的边界。后续应根据代表性回放判断是否需要更多轮次或按假设的读取参数，不能只把全部上限放大。

## 已落到代码的调整

| 场景 | 默认请求预算 | 模型与行为 |
| --- | --- | --- |
| 目标识别 | 10 秒；兼容旧 quick 配置 | 可走快速模型；超时最多重试一次，无可靠目标则澄清 |
| 调查规划 | 60 秒、2048 输出 token | 使用主模型；独立思考开关；一次较长调用，失败保留规则调查，不重复整轮推理 |
| 诊断事实选择 | 30 秒、512 输出 token | 可走快速模型；只选择已有事实编号，程序验证后渲染 |
| 整个任务 | 默认 300 秒、20 次模型调用、累计 100000 token | 所有阶段共用，原有持久预算和取消机制继续生效；每次输出还受任务级上限约束 |

配置位于 `rover.agent.llm`。目标识别的新键为 `target-timeout-seconds`，未设置时兼容旧 `quick-timeout-seconds`；规划独立使用 `planning-timeout-seconds`、`planning-max-output-tokens`、`planning-thinking-enabled`、`planning-evidence-context-chars`；报告使用 `report-timeout-seconds`。旧 quick 配置不再影响规划，这是有意的迁移变化。

各场景实际超时仍取场景配置与模型宿主配置中的较小值。例如宿主设 30 秒、规划设 60 秒，实际仍为 30 秒；需通过既有模型设置调整宿主上限，代码不会修改用户落盘的配置或密钥。任务已有显式总时限时仍尊重其配置；从持久状态恢复时沿用原截止时间，不因新默认值延长旧任务。

规划思考开关默认 false，与当前已验证模型行为保持一致；可独立打开，不再由“是否轻量调用”强制决定。供应商是否支持该参数、思考消耗是否挤占输出，仍需按模型回放验证。打开思考和使用更长时间都不能自行保证质量提升。

证据上下文默认 24000 字符，优先保留现有假设所引用的证据及 AVAILABLE/PARTIAL 观测；摘要由 160 提升为 1200 字符，并单独保留样本分组、原生最终响应统计、覆盖范围和变更关联等白名单字段。原始追踪行不整包塞入规划提示词。单项结构化事实上限 6000 字符，达到预算会明确标注截断或省略，不能由缺失内容推断正常。该预算只约束证据块，整个请求仍受任务 token 预算约束。

每轮可请求最多三个新候选、六个步骤；新增候选每轮硬上限为三、任务累计仍为六。所有候选保持 UNKNOWN，能力、资源、只读性及必查项继续校验。模型选中必查能力时不能将它降为可选；计划校验先为必查项分配步骤额度，再接受可选建议，避免扩大探索后挤掉基础取证。供应商返回 `finish_reason=length` 时，即使前缀看似合法 JSON，也拒绝采纳不完整计划。

还修复了真实回放发现的 H6 归因错误：旧的实例转发统计 `status5xx` 包含后端响应和网关生成错误，但规则曾将其写成“后端实例返回了 5xx”。H6 现在只确认“访问某实例时转发窗口出现 5xx”，明确该统计不能确认响应来源或业务根因；响应来源仍需原生窗口或逐请求证据。指标端口和快照的口径说明一并更正，没有把聚合 5xx 猜成后端 5xx。

## 验收与仍需证明的事

最终源码执行 `mvn -pl rover-admin -am verify`：common 20、core 118、runtime 227、admin 116，合计 **481 项通过**，零失败、错误或跳过；日志为 `.tmp/s2-product-alignment-origin-verify.log`，构建包含模型配置页文案和 H6 来源口径修正。中途一次 JVM 因 Windows 分页文件不足而未启动，改为显式较小启动堆后完整重跑；没有修改系统配置，也没有终止用户已有服务。

新增检查包括实际 HTTP 响应等待 11 秒仍完成、配置快速模型后规划仍使用主模型、思考参数独立传递、超时不重复整轮规划、供应商输出截断拒绝、共享调用/token/截止时间预算不重置、摘要尾部关键线索与两版本分母保留，以及可选步骤不能挤掉或降级必查项。脚本模型只证明调用契约，不能冒充模型语义质量评测。

Python 故障回放检查 **15 项通过**；真实模型任务的回放等待上限同步为 360 秒，以覆盖 300 秒任务预算和收尾。模型配置页两处用途说明更新，`node --check` 语法检查通过；没有新增交互或视觉布局。
