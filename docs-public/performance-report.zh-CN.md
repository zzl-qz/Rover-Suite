# 性能报告与压测方法

这份文档说明 Rover-Suite 当前的一组本地参考结果。若你准备在自己的机器上做容量评估，建议先阅读[性能测试指南](./benchmark-guide.zh-CN.md)，再按本文格式整理结果。

## 1. 先看结论

Rover-Suite 不提供通用 QPS 承诺。真实吞吐会受到 CPU/JDK、容器限额、路由数量、上游耗时、连接复用、网络位置、指标窗口和追踪采样率影响。

当前仓库记录的是 **本地 Docker Desktop 参考样本**（2026-08-25 更新：含代理流式回写优化前后对比）。它能说明在受限资源下 Gateway 链路可以跑通并观察开销，但不能直接代表 Linux 生产环境 SLA。

如果要给自己的环境做容量判断，建议直接复用本文命令，在目标机器上跑出自己的数据。

### 1.1 每一波、每种场景分别怎样（先看这张表）

环境都是本机 Docker Desktop、`perf-fair`（Gateway **2 核 / 2G**）。数字是当轮真实 `hey`，**没测过的格子写「未复测」，不编。**

**小 JSON：`GET /api/hello`**

| 波次 | 改了什么 | 稳态 c=50（成功 QPS / 错误） | 高压 c=100（成功 QPS / 错误） | 一句话 |
| --- | --- | --- | --- | --- |
| 第一波 | 上游响应改流式回写（出站仍是 JDK） | 约 **2576→2088（−19%）**，全 200 | 约 **1795→2347（+31%）**；503 **约 90%→2%** | 小包稳态不涨，高压少拒服 |
| 第二波 | 静态上游改配置期快照 | 保留率 **11.97%→12.13%**（约 2025→2215） | 不是这刀的点 | **不抬 QPS**，对齐热更新正确性 |
| 第三波 | 关观测 + hop-by-hop 常量；EventLoop 是试验 | 保留率 **12.13%→12.53%**（约 2215→2138） | EventLoop 试验：503 **约 2%→12%** | **几乎不抬**；EventLoop 默认关掉 |
| 第四波 | 出站换 Netty（JDK 路径留着） | 约 **2100→6800（约 3.2 倍）**；相对直连 **12%→40%**；全 200 | 成功约 **8830**；503 约 **5.6%** | **唯一拉开小包 QPS 的一刀** |
| 第五波 | 入站去掉 Aggregator，body 走管道 | 补测约 **6610**，全 200；和 6800 同一档 | 补测成功约 **8300～8400**；503 约 **4%** | **GET hello 不涨**；POST 才能叠连接 |

**大响应：`GET /api/payload?size=N`（c=20）**

| 场景 | 第一波流式 vs 整包 | 当前代码复测（第四+五波后，`184143`） |
| --- | --- | --- |
| 256 KB / 1 MB / 4 MB QPS | 和整包 **接近（±5%）** | 对比第一波流式：约 **918 / 228 / 70**（**−5% / −14% / 持平**），**不涨** |
| Gateway 内存 | 约 **−55%～−65%**（4 MB：约 1.2 GiB → 约 440 MiB） | 再降一截：约 **170 / 189 / 278 MiB**（4 MB 相对第一波流式约 **−37%**） |

**大请求体：`POST /api/ingest`（第五波该看的场景，c=20，首次）**

| 大小 | Gateway 成功 QPS（中位） | 当轮直连 | 约为直连 | Gateway 内存 |
| --- | ---: | ---: | ---: | ---: |
| 256 KB | 约 **808** | 约 1232 | **66%** | 约 267 MiB |
| 1 MB | 约 **239** | 约 285 | **84%** | 约 267 MiB |
| 4 MB | 约 **66** | 约 84 | **78%** | 约 302 MiB |

第二、三波仍没有单独大包 A/B（那两刀不碰 body）。第四波 JDK 半场 GET 的 Direct 自己掉了，**不能**拿后半场绝对 QPS 吹大包更快。明细见 §8.3。

**能对外说的累计（稳态小包）：** JDK 出站时期约 **2100 QPS / 直连 12%** → 现在约 **6800 QPS / 直连 40%**。涨出来的那一截，几乎全是第四波。第一波赢的是高压成功率和大包内存；后面几波大包 QPS 仍不涨，内存又低了一截。

## 2. 为什么这组数据看起来不够直觉

当前样本里有两个容易让人疑惑的点：

1. **直连 demo 的 P95/P99 有时比 Gateway 更高。**  
   这通常说明尾延迟受 Docker Desktop 调度、宿主机状态或 demo 容器抖动影响。它不表示 Gateway 能优化上游尾延迟。更稳的做法是增加轮次，记录原始 `hey` 输出，并补充 CPU、GC 和容器资源曲线。

2. **Gateway 并发 100 在旧实现下会出现大量 503。**  
   这组数据已经进入 Gateway 资源瓶颈。流式回写后成功吞吐明显回升（见 §1.1 / §7.2），但仍不适合把 c=100 与 c=50 的稳定吞吐简单相除。

所以这组数据定位为 **参考样本**，不是正式基准。后续如果要增强说服力，建议补齐原始输出、机器型号、Docker 配置、CPU 曲线、GC 日志和多轮统计。

## 7. 代理流式回写优化（2026-08-25）

### 7.1 改了什么

- **之前**：上游响应在 `HttpProxyClient` 内聚合成完整 `byte[]`，再包装为 `FullHttpResponse` 一次性写出。
- **现在**：边收边写 `HttpResponse` + `HttpContent`，不再为响应体整包分配堆数组。
- **当时未改**：入站仍整包 `FullHttpRequest`；出站仍是 JDK `HttpClient`（这条后来还在，见 §8.2）。

### 7.2 结论（简）

| 场景 | 变化 | 说明 |
| --- | --- | --- |
| 小 JSON（`/api/hello`，c=50） | 成功 RPS 约 **−19%** | 分帧开销大于拷贝收益 |
| 小 JSON（c=100 高压） | 成功 RPS **+31%～+36%**；503 约 **90%→2%** | 主要改善稳定性，不是 P50 |
| 大包（256 KB～4 MB，c=20） | 成功 RPS 与整包 **接近**（±5%） | 带宽/上游已是瓶颈 |
| 大包 Gateway 内存（压测采样） | 约 **−55%～−65%** | 4 MB 负载：整包约 1.2 GiB → 流式约 440 MiB |

**一句话**：流式回写不是「所有接口 QPS 都涨」，而是 **大响应更省内存、高压下更少 503**；小接口极限 QPS 可能略降。

### 7.3 JDK 出站时期的容量口径（2 核 / 2G，本机 Docker Desktop）

这组数是 **出站还是 JDK `HttpClient`** 时的拐点，**不是 SLA，也不和 Nginx / Envoy 比裸 QPS**。换 Netty 出站之后的数字见 §8.2。

| 档位 | 并发（hey `-c`） | 成功吞吐（约） | 错误 | 怎么读 |
| --- | ---: | --- | --- | --- |
| 稳态（JDK 出站） | 50 | 约 2100 QPS，P50 约 14 ms | 0 | JDK 时期能对外说的稳定区 |
| 拐点（JDK + 业务线程池） | 100 | 成功约 2300 QPS | 约 2% 503 | 历史样本；不要把 503 算进成绩 |
| 拐点（JDK + EventLoop 试验） | 100 | 成功约 2280 QPS | 约 12% 503 | 历史样本；默认仍是业务线程池 |

同机直连 Demo 当时约 1.7～1.8 万 QPS。Gateway 大约保留直连的 **12%**。换 Netty 出站后稳态约 **6800 QPS / 保留约 40%**，见 §8.2。

### 7.4 适用场景

- 推荐：文件下载、导出、大 JSON、响应体大小不确定、容器内存紧张、高并发代理。
- 不单独依赖流式优化的：极小 JSON 的极限延迟；仍需 Filter 读完整请求体的路径（需另有界缓冲）。

### 7.5 优缺点

| | 整包缓冲 | 流式回写（当前默认） |
| --- | --- | --- |
| 实现复杂度 | 低 | 较高 |
| 小响应 QPS | 略高 | 略低（本机样本） |
| 高压成功率 | 易出现大面积 503 | 成功吞吐明显更高 |
| 大响应内存 | 高，易顶满容器限额 | 显著降低 |
| 大响应 QPS（低并发） | 与流式接近 | 与整包接近 |

## 8. 静态上游快照（2026-08-25）

### 改了什么

静态路由不再在每个请求里 `URI.create` + 组装 `ServiceInstance`。路由启动和热更新时 `StaticUpstreamCluster.rebuild` 算一次，请求只读快照。Admin 改路由仍走 `applyRoutes`，快照与 matcher 一起换，不会打到旧上游。

### 怎么测才算合格

隔几小时拿两组 Phase A 互相对照，若 **Direct 自己先变了**，整组作废。  
合格条件：同一时段先后打「无快照 / 有快照」，每边都先打 Direct；**Direct c=50 中位差 ≤ 10%** 才对比 Gateway。

合格 run：`2026-08-25-132633-phase-a-static-ab`（Direct 漂移 **7.8%**，过门）。  
作废：`2026-08-25-130701-phase-a-static-cache`（对照隔次 Direct，差约 12%）。

### 结论（同场、已归一化）

| 模式 | Direct c=50 | GW 静态 c=50 | 相对当轮 Direct |
| --- | ---: | ---: | ---: |
| 无快照（每请求 resolve） | 16949 | 2025 | **11.97%** |
| 有快照 | 18271 | 2215 | **12.13%** |

绝对 QPS 两边都随 Direct 起伏。用当轮 Direct 归一化后，Gateway 保留率几乎一样（约 12%）。  
**不能对外说「缓存提升了吞吐」。** 那一刀对齐配置期预计算，正确性在；当时天花板仍是 JDK 出站。当前数字见 §8.2。

## 8.1 关掉观测与 EventLoop（2026-08-25）

Phase A 当时关掉 metrics/trace，hop-by-hop 头改为常量比较，并把 Handler 留在 EventLoop（试验配置）。  
run：`2026-08-25-141900-phase-a-obs-off`。Direct 对比上一合格轮 −6.6%（过 10% 门闩）。当前代码默认已改回 `dispatchOnEventLoop=false`。

| | Direct c=50 | GW 静态 c=50 | 当轮保留率 | c=100 503 |
| --- | ---: | ---: | ---: | ---: |
| 快照合格轮（观测开 + 业务线程池） | 18271 | 2215 | 12.13% | 约 2% |
| 本轮 | 17057 | 2138 | **12.53%** | **约 12%** |

关掉观测、少做 `toLowerCase` **几乎不抬吞吐**。EventLoop 直跑没有拉开稳态 QPS，却让高压拒绝变多。三刀捆在一起测的，没有单独拆开。

## 8.2 Netty 出站（2026-08-25）

默认出站现在是 Netty（`rover.gateway.proxy.outbound: netty`）。第一版 JDK `HttpClient` HTTP/1.1 还在（`outbound: jdk`），兼容性踩坑没有删。

run：`2026-08-25-152000-phase-a-netty-outbound`。同一套 `perf-fair` / Phase A / 业务线程池 / 关观测。Direct c=50 中位 **16939**，对比 `141900` 为 **−0.7%**，对比 `132633` 为 **−7.3%**（都过 10% 门闩）。

| 时期 | Direct c=50 | GW 静态 c=50 | 当轮保留率 | GW P50 | c=100 成功 QPS | c=100 503 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 快照（JDK） | 18271 | 2215 | 12.13% | 13.0 ms | 约 2460 | 约 2% |
| 关观测（JDK + EventLoop 试验） | 17057 | 2138 | 12.53% | 15.5 ms | 约 2280 | 约 12% |
| **Netty 出站（当前）** | **16939** | **6795** | **40.1%** | **5.6 ms** | **约 8830** | **约 5.6%** |

Nameserver 路径 c=50 中位 **7266**（当轮 Direct 的 42.9%），全 200。和静态同一档，不是发现税。

**怎么读**

- 稳态大约是 JDK 出站合格轮的 **3.1～3.2 倍**。这是 Phase A 里第一刀真正拉开「相对直连约 12%」天花板的改动。
- 能当稳定区的仍是 c=50（全 200）。
- c=100 仍有拒绝：报 **成功** QPS（约 8830）和约 5.6% 的 503。不要把掺了 503 的总 QPS（约 9360）当成绩。
- 入站已去掉 `HttpObjectAggregator`（头到了就转发，body 走管道）。Phase A 复测：GET hello **不涨**（约 6610 vs 本表 6800，同一档）。**容量口径仍按本表 Netty 出站数字说。**

当前 2 核 / 2G 本机口径：**c=50 / 约 6800 QPS / 全 200 / 约为直连的 40%**。

同场 A/B（`2026-08-25-154500-phase-a-outbound-ab`）：同一镜像只改 YAML，启动日志核对过（`JDK HttpClient HTTP/1.1` vs `Netty`）。Direct c=50 漂移 **3.3%**。JDK 半场：GW **1865** / 直连 **12.0%**。Netty 半场：GW **6615** / 直连 **43.8%**。同一 jar 大约 **3.5 倍**。两边 c=50 都是全 200。

## 8.3 大包 / POST 复测（2026-08-25，`184143`）

当前代码（响应流式 + Netty 出站 + 入站管道），`perf-fair`，c=20，20s，3 轮中位。脚本：`bench-phase-a-payload-remasure.sh`。对照第一波流式：`123108`。

**GET `/api/payload`（Netty 出站，全 200）**

| 大小 | 第一波流式 QPS | 本轮 QPS | 变化 | 第一波流式内存 | 本轮内存 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 256 KB | 971 | **918** | **−5%** | 352 MiB | **170 MiB** |
| 1 MB | 266 | **228** | **−14%** | 355 MiB | **189 MiB** |
| 4 MB | 69 | **70** | **持平** | 439 MiB | **278 MiB** |

本轮 Direct：1161 / 294 / 81，和第一波流式 Direct（1189 / 288 / 76）同档，对照成立。  
**大包 QPS 仍不涨**（带宽/上游还是主瓶颈）。内存比第一波流式再低一截，4 MB 约 **440→280 MiB**。

**POST `/api/ingest`（首次，Netty 出站，全 200）**

| 大小 | Gateway QPS | Direct | 约为直连 | Gateway 内存 |
| --- | ---: | ---: | ---: | ---: |
| 256 KB | **808** | 1232 | **66%** | 267 MiB |
| 1 MB | **239** | 285 | **84%** | 267 MiB |
| 4 MB | **66** | 84 | **78%** | 302 MiB |

没有旧 Aggregator 对照，这是基线，不是「比以前涨了多少」。4 MB POST 同场 JDK 出站 QPS 约 62（Direct 两边都是 84），**QPS 几乎一样**；JDK 出站内存约 **790 MiB**，明显高于 Netty 的约 300 MiB。

JDK 半场 GET 的 Direct 自己掉了（256K 1161→663），那组绝对 QPS **作废**，不要用来讲第四波大包更快。

## 9. 如何让压测结果更可信

如果准备把压测结果用于发布说明、选型或容量规划，建议补齐这些材料：

1. 保存每一轮 `hey` 原始输出。
2. 至少跑 5～10 轮，并记录均值、最小值、最大值和标准差。
3. 同时记录 Gateway、Nameserver 和上游的 CPU、内存、GC、线程数。
4. 把 Admin 关闭，或说明 Admin 页面是否开启实时轮询。
5. 固定路由数量、上游响应体大小、连接复用策略和日志级别。
6. 在目标 Linux 环境重跑，不直接使用 Docker Desktop 数据做生产判断。
7. 对异常样本保留说明，不把错误状态码的结果混入成功吞吐。

## 10. 本文数据怎么使用

这组数据可以作为本地开发和小资源档位的参考起点。它不能作为项目性能承诺，也不建议用于和其他 Gateway 产品做正式横向对比。

更可靠的做法是：把本文命令复制到目标环境，保留原始输出，再结合业务路由、上游耗时和资源限制生成自己的报告。
